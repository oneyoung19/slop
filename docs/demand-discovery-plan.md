# 需求发现与开发机会分析：Plan & Todo

更新日期：2026-09-22  
状态：需求设计初稿，待逐阶段确认与实现  
用途：后续迭代的需求依据、实施计划和进度记录。本轮仅创建文档，不实现页面、采集服务或定时任务。

## 1. 已确认的目标

建立公开的需求分析页面，自动发现候选产品，从产品及用户反馈中识别痛点，帮助站点作者决定下一阶段开发什么。

- **方向不限**：不预先限制为 AI、插件、CLI 或某类行业。
- **自动发现**：用户不需要提前知道产品、输入主题或提供链接。
- **快速实现**：优先筛选单人约一周内能完成最小可验证版本的机会。
- **付费潜力**：关注明确付费人群、问题造成的成本及现有付费替代方案。
- **公开浏览**：先公开展示分析结果，账号、权限与个人工作流后续迭代。
- **先讨论再实现**：本文件记录整体方案；下一阶段按 Todo 推进，不能把待决策项当作已确认需求。

成功标准不是收集更多热门产品，而是提供少量、有证据、范围明确、可以进一步验证的开发机会。自动发现不等于自动证明市场需求。

## 2. 第一版产品范围

### 必须包含

1. 从选定来源自动发现候选产品，无需用户提供链接。
2. 补充候选产品的公开用户反馈与产品背景。
3. 将反馈整理成可追溯的痛点与开发机会。
4. 判断一周 MVP 的可行性、付费依据及主要不确定性。
5. 公开展示机会列表与详情，支持基础筛选和排序。
6. 显示分析时间、来源覆盖范围、采集失败或资料不足等状态。

### 暂不包含

- 访客公开触发采集或付费 AI 分析。
- 账号系统、个人收藏、团队权限、私有备注与协作看板。
- 自动生成代码、自动创建项目或自动发布产品。
- 全网采集、所有平台同时接入、实时更新。
- 没有依据的营收预测、市场规模数字或“必然有人付费”的结论。

### 建议的运行方式（待确认）

把“自动发现候选”与“何时运行”分开：第一版提供可手动启动的完整自动采集流程，启动后不需要人工找产品；验证质量和成本后再开启每日或每周定时运行。

公开页面只读取已保存的结果。流水线通过本地命令或受控的 CI 操作触发，不在公开页面放无鉴权的运行按钮。这个边界不要求第一版建设用户权限系统。

## 3. 信息来源与证据要求

GitHub Trending、Product Hunt 是用户提出的候选入口。具体接口、访问条件、限额、条款、可用字段及稳定性尚未调研，以下为目标能力，不是已验证的接入承诺。

| 来源 | 发现产品的用途 | 痛点证据 | 实现前需要确认 |
| --- | --- | --- | --- |
| GitHub Trending 或其他 GitHub 发现入口 | 找到近期受到关注或持续活跃的仓库 | Issues、公开讨论、功能请求、重复的使用障碍 | Trending 获取方式；官方 API 能覆盖什么；限流与分页 |
| Product Hunt | 找到新产品和对应使用场景 | 公开评论、提问、产品定位及定价信息 | API 授权、评论字段、使用与公开展示条件 |
| 产品官网或文档 | 理解已有能力和替代方案 | 公开价格、功能限制、使用流程 | 是否允许读取；内容时效；缺失信息处理 |

实施建议：先打通一个稳定来源，再补充第二个来源；不能因某个来源未接通而伪造其候选或反馈。GitHub 替代发现入口必须如实标注，不能标为 Trending 榜单。

### 信号分类

- **事实**：来源中明确出现的功能、价格、问题和反馈。
- **需求信号**：具体用户在具体场景中遇到的障碍，保留原始链接与时间。
- **分析推断**：AI 对共同痛点、产品方向、商业方式的推导，明确标记为推测。
- **证据不足**：找到了产品，但未找到足够的用户反馈；不包装成已验证机会。

热度只用于发现候选，不直接作为付费潜力得分。一个 issue 的多次回复不等于多个独立需求；同一内容跨平台转载需要去重。

## 4. 自动发现与分析流程

`发现候选 → 去重与初筛 → 收集证据 → 提取痛点 → 聚合同类需求 → 评估 MVP 与付费潜力 → 质量校验 → 保存并公开展示`

1. **发现候选**：按时间窗口获取产品；记录来源、外部 ID、链接和发现时间。
2. **去重与初筛**：合并同仓库、同域名、同产品的重复条目；避免结果被单一技术或类别占满。
3. **收集证据**：先收集产品背景，再获取有上限的相关反馈；长线程先筛选再分析。
4. **提取痛点**：描述“谁，在什么场景，为完成什么任务，被什么问题阻碍”。没有证据则保留为候选。
5. **聚合需求**：多个产品可能暴露同一个痛点；一个产品也可能对应多个不同机会。
6. **机会分析**：输出付费人群、替代方案、最小产品范围、一周拆解、获客入口、验证办法与风险。
7. **质量校验**：校验结构、引用是否存在、结论与证据是否一致，以及是否满足发布门槛。
8. **保存结果**：保留运行记录与分析版本；失败时继续展示上一次成功结果，并注明更新时间。

### 运行约束

- 每次运行配置候选数、每个候选的证据条数、AI 调用量和费用上限；具体数值在试运行后确定。
- 只有通过初筛的候选进入较昂贵的深入分析。
- 按来源 ID、更新时间与内容摘要判断是否需要重新分析。
- 超时、限流、部分来源失败分别记录；有限重试，不无限循环。
- 同一批次重复运行不生成重复机会；发布新快照应原子完成，避免半成品覆盖正常结果。
- 外部内容仅作分析材料，不执行其中的指令，也不自动访问任意未校验链接。

## 5. 机会评估方式

第一版建议显示分项判断与依据，不用缺乏校准的综合分数制造精确感。

| 维度 | 判断问题 | 建议输出 |
| --- | --- | --- |
| 一周可行性 | 单人能否在约 5–7 天内做出可供目标用户试用的核心流程？ | 符合 / 有条件符合 / 超出范围；依赖与范围说明 |
| 付费潜力 | 谁购买、谁使用、解决问题能省什么成本？ | 较强 / 待验证 / 较弱；列出事实与假设 |
| 证据强度 | 是否有独立、具体、近期的反馈？ | 多条独立反馈 / 单条反馈 / 仅产品信息 |
| 获客可行性 | 第一批潜在用户在哪里？ | 可触达渠道与验证动作 |
| 竞争与缺口 | 已有方案为何还没解决这个问题？ | 差异点、替代方案及可能的反证 |

推荐排序：优先一周可行性明确、具有具体付费依据、证据可追溯的机会，再比较更新时间。未知付费潜力不能默认为高。

建议的公开机会最低门槛：至少一条可追溯的具体痛点证据，并明确注明证据强度。仅有产品描述或热度的条目进入“候选 / 证据不足”，不进入推荐机会列表。门槛在样本评审后可调整。

“一周”指一个聚焦的 MVP，不承诺一周完成全部商业化、复杂合规、销售和持续运营；估时必须写明技能、现成组件和外部服务等前提。

## 6. 页面与交互设计

### 导航与路由（建议，待确认）

新增 `Discover` 导航，与 Home、Projects、About 并列。

- `/discover`：开发机会列表。
- `/discover/[slug]`：机会详情。

页面名称与界面语言尚未最终确认；现有站点是英文界面，分析正文建议优先中文，来源名称保持原文。

### 列表页

- 页头：页面用途、最近成功更新时间、实际启用的数据来源。
- 来源异常或数据陈旧提示：清楚说明本次覆盖不足，区分“未发现机会”和“没有采集成功”。
- 基础筛选：来源、一周可行性、付费潜力；分类从结果中归纳，不预设领域限制。
- 排序：推荐、最新发现。
- 机会卡片：痛点标题、目标用户、机会摘要、MVP 预估、付费依据、证据数量与强度、更新时间。
- 点击进入详情；保留筛选条件，支持分享带条件的 URL。
- 无结果、数据尚未生成、加载失败分别呈现，不用假数据补位。

### 详情页

1. **机会概览**：一句话痛点、适用人群、为何值得关注。
2. **原始证据**：简短摘要、来源链接、时间，区分事实和推测。
3. **已有方案与缺口**：已有产品能做什么、用户为什么仍有问题、反例。
4. **一周 MVP**：必须完成的核心流程、明确不做的内容、逐日建议与依赖风险。
5. **付费假设**：购买方、价值、已有付费替代；价格建议只能标为待验证假设。
6. **先验证什么**：低成本验证动作、需要询问目标用户的问题、继续或放弃的信号。
7. **分析信息**：生成时间、证据时间、来源覆盖和主要局限。

第一版不把公开的收藏或“已选中”操作实现为全站共享状态。个人收藏、忽略、转为项目需求草稿留到后续权限阶段。

## 7. 数据结构草案

### Candidate：候选产品

`id`、`source`、`sourceId`、`name`、`url`、`canonicalUrl`、`description`、`discoveredAt`、`sourceUpdatedAt`、`category`、`discoverySignals`、`collectionStatus`。

### Evidence：证据

`id`、`candidateIds`、`source`、`url`、`publishedAt`、`collectedAt`、`summary`、`kind`、`contentHash`、`availability`。

公开展示简短摘要与来源链接，避免默认保存和展示整篇外部内容或不必要的个人信息。时间未知时明确为空，不用抓取时间冒充发布时间。

### Opportunity：开发机会

`id`、`slug`、`title`、`candidateIds`、`targetUser`、`painPoint`、`evidenceIds`、`inferences`、`alternatives`、`mvpScope`、`outOfScope`、`estimatedDays`、`estimateAssumptions`、`paymentHypothesis`、`paymentEvidenceIds`、`acquisitionChannels`、`validationPlan`、`risks`、`feasibility`、`paymentPotential`、`evidenceStrength`、`publicationStatus`、`analyzedAt`、`analysisVersion`。

### AnalysisRun：分析批次

`id`、`startedAt`、`finishedAt`、`sourceStatuses`、`candidateCount`、`evidenceCount`、`opportunityCount`、`failures`、`model`、`promptVersion`、`usage`、`estimatedCost`、`snapshotVersion`。

凭据、原始运行日志和内部调试信息不得进入公开数据快照。

## 8. 与当前项目的集成方案

### 已检查的项目事实

- 项目使用 Next.js App Router。
- `next.config.ts` 配置了 `output: "export"`。
- 已有 GitHub Actions 构建并部署 GitHub Pages 的流程。
- GitHub Actions 环境使用 `/slop` basePath，新页面链接和数据资源必须兼容该路径。

### 推荐的第一版架构

采用“独立采集与分析任务 + 持久化结果快照 + 静态公开页面”。

- 外部 API 和模型调用在本地脚本或 CI 中执行，凭据保存在环境变量 / CI Secrets。
- 任务输出经过校验的、适合公开的数据快照。
- 页面构建时读取快照，生成列表与详情；新机会更新需要重新构建和部署。
- 快照必须跨运行保留，不能只存临时 CI artifact 后依赖其长期存在。
- 实施前确定快照存储方式：独立数据分支、仓库内审核后提交，或外部持久化存储；暂不默认给 CI 自动写主分支权限。
- 抓取失败不阻断已有内容展示；首次无数据要明确显示尚无分析结果。

这一方案可沿用当前静态部署。只有确认需要访客提交任务、账号和实时分析后，再评估后台服务、数据库和任务队列。

## 9. Plan：实施阶段

### P0：确认来源与产品边界

目标：确认可以合法、稳定地获取候选与证据，以及一周 MVP 和付费潜力的评判方式。

交付：来源可行性记录、若干真实样本、分析输出模板、第一版成本上限和运行方式决定。

退出条件：至少一个来源能自动发现候选并取得可追溯反馈；若不满足，应更换来源或降低覆盖范围，不进入无数据的页面开发。

### P1：打通一次真实的自动发现与分析

目标：无需输入产品链接，运行一次即可产生候选、证据与合格机会；低证据结果可以为空。

交付：来源适配器、分析流水线、结构校验、去重、预算限制、结果快照和运行报告。

退出条件：人工抽查每条样本的证据、估时和付费假设；重复运行不重复生成，部分失败有记录。

### P2：实现公开页面

目标：让访客能够浏览、比较和追溯机会。

交付：导航入口、列表、详情、筛选排序、状态提示、响应式布局和元数据。

退出条件：真实数据可展示；筛选和返回路径经浏览器验证；静态导出和 basePath 下工作正常。

### P3：稳定运行并决定自动更新频率

目标：形成可持续更新的流程，明确费用与失败恢复。

交付：持久化与发布流程、有限重试、数据陈旧提示、成本记录；确认后配置定时运行。

退出条件：来源失败仍保留上次成功结果；运行不泄露凭据；更新后页面能够看到新结果。

### P4：后续扩展

根据真实使用反馈决定：更多来源、账号权限、收藏忽略、个人偏好、转需求草稿、机会验证记录，以及实际开发后的价值反馈。
